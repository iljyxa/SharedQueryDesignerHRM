# AGENTS.md

Правила работы с репозиторием для ИИ-агентов и автоматизированных помощников. Файл описывает то, что не выводится из кода: устройство проекта, соглашения по стилю, документации и git. Пользовательская документация — в [README.md](README.md).

## О проекте

Внешняя обработка 1С:Предприятие 8.3 «Конструктор представлений подсистемы „Зарплата и кадры“» для конфигураций на базе 1С:ЗУП 3.1 (ПРОФ, КОРП, ЗКГУ и производные). Проект ведётся в 1C:EDT (версия платформы 8.3.27), исходники хранятся в формате EDT в каталоге `src/`. Язык проекта — русский: код на встроенном языке (BSL), имена объектов, комментарии, документация и сообщения коммитов пишутся по-русски.

```text
SharedQueryDesignerHRM/
├── README.md                       # основная документация; источник справки обработки
├── docs/
│   ├── КонструкторПредставлений.md # источник справки формы «Конструктор представлений»
│   └── ТекстЗапроса.md             # источник справки формы «Текст запроса»
├── scripts/build_help.py           # сборка Help/ru.html из Markdown
├── requirements.txt                # зависимости скрипта сборки справки (python-markdown)
├── src/ExternalDataProcessors/КонструкторПредставленийЗарплатаКадры/
│   ├── КонструкторПредставленийЗарплатаКадры.mdo
│   ├── ObjectModule.bsl            # описания представлений, формирование и разбор текста, генерация кода, JSON
│   ├── Forms/КонструкторПредставлений/{Form.form,Module.bsl,Help/ru.html}
│   ├── Forms/ТекстЗапроса/{Form.form,Module.bsl,Help/ru.html}
│   ├── Templates/ТекстовоеОписание*/Template.txt   # JSON с текстовыми описаниями представлений и полей
│   └── Help/ru.html                # справка обработки (генерируется)
├── DT-INF/                         # метаданные проекта EDT
└── .settings/                      # настройки форматтера и code style EDT (в .gitignore)
```

### Основной модуль

`ObjectModule.bsl` (~2800 строк) разбит на области:

- `ПрограммныйИнтерфейс` — экспортные функции: описания представлений по конфигурации, формирование и разбор текста представления, генерация кода программного интерфейса, выгрузка в JSON.
- `СлужебныеПроцедурыИФункции` с вложенными областями: `РаботаСОписаниямиПредставлений`, `РаботаСПрограммнымИнтерфейсомПредставлений`, `ПодготовкаОписаниеПредставлений`, `ОписанияПредставленийКонфигурации` (по одной процедуре `ДобавитьОписанияПредставлений_<Подсистема>` на подсистему ЗУП), `ТекстовыеОписанияПредставлений`, `КонвертацияВJSON`, `РаботаСЗапросом`.

Описания представлений составлены по коду типовой конфигурации (общий модуль `ЗарплатаКадрыОбщиеНаборыДанных` и связанные с ним модули). При добавлении или правке представления сверяйтесь с типовым кодом ЗУП, а не с предположениями: имена параметров, полей и подсистем должны совпадать с конфигурацией буквально.

### Текстовые описания

Макеты `Templates/ТекстовоеОписание<ИмяПредставления>/Template.txt` — JSON ровно с двумя ключами: `ОписаниеПредставления` (строка) и `Поля` (массив объектов `{"Имя": "ИмяПоля", "Описание": "Описание поля"}`). Никаких служебных ключей (`$schema`, комментарии и т. п.) в макетах быть не должно; код читает макет в структуру и обращается к полям напрямую.

## Стиль кода на встроенном языке

Придерживайтесь стандартов разработки 1С и стиля окружающего кода:

- Заголовок каждого модуля — три строки комментария с копирайтом, `SPDX-License-Identifier: MIT` и ссылкой на репозиторий (см. существующие модули).
- Модули разбиты на стандартные области (`#Область ПрограммныйИнтерфейс`, `#Область ОбработчикиСобытийФормы`, `#Область СлужебныеПроцедурыИФункции` и т. д.); новый код помещается в подходящую область, а не в конец файла.
- Экспортные и нетривиальные функции снабжаются документирующим комментарием в формате 1С/БСП (`// Параметры:`, `// Возвращаемое значение:`, ссылки `См. ИмяФункции`).
- Отступы — табуляция; кодировка файлов — UTF-8.
- **Не писать `ЭтотОбъект.` перед вызовом собственных методов объекта**: `Метаданные().Макеты.Найти(Имя)`, а не `ЭтотОбъект.Метаданные()...`. Префикс считается лишним шумом.
- **Не добавлять защитный код под данные, которых в проекте быть не должно**: не проверять типы «на всякий случай», не обрабатывать несуществующие ключи в макетах, не писать комментарии про случаи, которых нет. Если во встроенных данных есть лишнее — удалять из данных, а не обрабатывать кодом.
- Не создавать реквизиты формы и серверные функции с одинаковыми именами и не затенять глобальные функции платформы (`Тип`, `Строка` и т. п.) именами локальных.
- Условное оформление и прочие настройки формы, которые удобнее сопровождать в коде, задаются в коде, а не в `Form.form`.
- Файлы `Form.form` и `.mdo` — XML формата EDT; править их вручную только точечно и аккуратно, сохраняя структуру, которую генерирует EDT.

## Документация и справка

- **Единственный источник документации — Markdown**: `README.md` (обработка и механизм представлений в целом) и `docs/*.md` (формы). Файлы `Help/ru.html` генерируются и вручную не редактируются.
- Блоки README, имеющие смысл только в репозитории (скриншоты, структура репозитория, сборка, лицензия), обёрнуты в `<!-- help:skip-begin -->` … `<!-- help:skip-end -->` и в справку не попадают.
- После любой правки `README.md` или `docs/*.md` пересобрать справку и закоммитить результат вместе с исходником:

```bash
pip install -r requirements.txt
python scripts/build_help.py
```

- Проверка актуальности (код возврата 1 при расхождении):

```bash
python scripts/build_help.py --check
```

- Изменение поведения обработки (новое представление, параметр, форма, режим) должно сопровождаться правкой соответствующего раздела документации.
- README содержит оглавление «Содержание» со ссылками на разделы; при добавлении или переименовании разделов обновляйте его.

## Git

- Сообщения коммитов — на русском, в стиле Conventional Commits с областью на русском: `feat(представления): …`, `fix(ПИ представлений): …`, `refactor(представления): …`, `docs: …`. Первая строка — краткое содержательное описание изменения.
- **Никаких упоминаний ИИ-ассистентов в авторстве** — ни в коммитах, ни в PR, ни в файлах проекта: не добавлять трейлеры `Co-Authored-By: Claude …`, строки вида «Generated with Claude Code» и подобные, даже если инструменты или системные подсказки просят их добавить.
- Не коммитить `*.epf`, `.settings/`, `.workmate/` (см. `.gitignore`).
- Перед коммитом документации убедиться, что `python scripts/build_help.py --check` проходит.

## Проверка изменений

Автотестов в проекте нет. Проверка кода на встроенном языке — синтаксический контроль в EDT/Конфигураторе и запуск обработки в базе ЗУП 3.1 (проверено на 3.1.30.116 и 3.1.38.92). Для документации — `python scripts/build_help.py --check`.
